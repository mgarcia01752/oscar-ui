## Compatibility and migration

Installations without a compatible baseline need one full MSI installation
before subsequent compatible patches can be applied. jpackage's old version-dependent ProductCode and JAR filename do
not support this patch family. We still use jpackage for the application image;
explicit WiX authoring now owns the MSI, stable component identities, branded
wizard and shortcuts. The installed JAR is `app/oscar-ui.jar`.

Only the immediately previous compatible release can update through an MSP.
The patch changes the application JAR and native launcher. Java, Qt, OSCAR,
other dependencies, helper, launcher configuration and file layout must match.
Their hashes and installer authoring establish a baseline fingerprint and stable
ProductCode. Changed dependencies/layout/authoring require a new baseline.
Skipped releases, missing metadata, development runs and unsupported locations
retain full-MSI instructions. Current automatic support requires Program Files.
Version numbers alone never establish compatibility.

## User flow

1. Startup checks once for a stable release; About supports manual retries.
   The green Update chip opens About and does not install silently.
2. A compatible release enables **Update on Windows**, displaying patch size.
   Save/discard checks and a confirmation precede closing OSCAR-UI.
3. The installed PowerShell helper downloads the exact patch with a cancellable
   progress window, bounded size, SHA-256 verification and a five-minute limit.
4. It waits up to two minutes for the application to exit, then asks to install
   and requests administrator approval. The elevated helper independently checks
   release metadata, registered product/version and installed dependency hashes.
5. Verified bytes are copied into protected staging and Windows Installer applies
   the MSP. The original, unelevated helper restarts the app on success. Exit 3010
   reports that a reboot is required instead of restarting.
6. Failure/cancellation shows a message and offers to reopen the application.
   Windows Installer owns rollback and repair; no direct JAR replacement occurs.
   Installer logs remain under `%SystemRoot%\Temp\OSCAR-UI-update-*`.

The download and manifest trust this project's GitHub HTTPS release and its
SHA-256 asset digests. This detects mismatches/corruption; it is **not** independent
publisher authentication or Authenticode signing. No signing certificate has
been introduced. Personal configuration contents are never sent to GitHub.

## Build, retention and publication

`scripts/build/windows-installer.py` authors the stable MSI and optional patch;
`scripts/windows/windows-msi.ps1` obtains verified previous release inputs and
runs WiX. Existing output directories are rejected; use a fresh build directory.
Local builds never install the generated patch. Hosted CI performs the lifecycle.

Each Windows release includes the full MSI, `windows-update.json` and
`windows-patch-inputs.zip`; compatible releases also include an MSP. The compact
ZIP retains only WiX symbols, input metadata, the previous launcher and JAR.
It does not duplicate Java/Qt/source archives. Preserve these assets and earlier
MSI/MSPs in the baseline family: later builds reconstruct and test the patch chain.
The chain guard stops after 20 patches and requires a new baseline. Published
versions are not regenerated by tagged builds.

The shared release coordinator resolves draft releases by numeric ID from the
authenticated release list; the tag endpoint does not resolve drafts. It verifies
the uploaded Windows assets and manifest
before publishing its draft. Ubuntu DEB behavior remains unchanged. End users
normally download the MSI; update metadata and inputs are consumed by automation.

## Production validation

Before publication, Windows CI tests previous full MSI → MSP → repeated MSP →
launch → normal/forced repair → uninstall, with exact installed file hashes and
registered version checks. For later patches, it additionally installs the
original baseline and previous patch chain before applying the target patch.
Synthetic user files outside the installation must survive. Reboot-required
results fail hosted lifecycle checks instead of being reported as launch success.

Portable tests cover family identity, changed dependency/layout rejection,
compact retention, Java compatibility and publication gates. The Windows helper
validation harness uses mocked registry/release data and never installs anything.
These checks do not prove UAC, interrupted-install rollback or Windows 11 behavior.
Keep those interactive cases pending in the checklist until actually exercised.

## Production patch validation

The standalone prototype workflow has been retired. The normal Windows release

## Shortcut validation and pre-release build

Run `39356912700` passed the duplicate-property link check, then failed MSI
validation ICE38/ICE43/ICE57: the non-advertised shortcut component used an HKLM
key path. Its registry key path now uses HKCU, as required for this shortcut
type; the package remains per-machine and retains Start menu/Desktop shortcuts
and uninstall cleanup. See Microsoft's [ICE43](https://learn.microsoft.com/en-us/windows/win32/msi/ice43).
Portable authoring tests cover this contract; they do not execute MSI validation.

Use the local Windows build helper for pre-tag packaging checks. On GitHub,
`release.yml` builds and verifies the MSI after tagged CodeQL and all OS checks
pass. Package jobs are no longer independently dispatchable on `main`.

A passing native build/install/launch/uninstall job is required before claiming
this fix is Windows-validated. Dispatching on `main` does not bump the version.

## Launcher version compatibility correction

The published v0.4.8 and v0.4.9 installers belong to different baseline families;
v0.4.9 has no MSP. The generated launcher configuration contained
`java-options=-Djpackage.app-version=<release>`, which incorrectly changed the
dependency fingerprint for every release. Comparing retained WiX file hashes
identified the configuration change. Replacing only this property in the actual
v0.4.8 MSI configuration reproduces the v0.4.9 configuration's MSI file hash.

Preparation now removes that redundant property before hashing. The application
and About still read their version from `build-info.properties` inside the JAR.
All other launcher options remain fingerprinted. Tests use realistic CRLF
jpackage configurations and prove version-only compatibility while rejecting
actual runtime-option changes.

This authoring correction requires a new full-MSI baseline; v0.4.8/v0.4.9 cannot
be used to test the corrected patch family. Do not label a subsequent release
patch-compatible until its manifest contains an MSP and its production patch
lifecycle has passed Windows CI. The earlier synthetic fixture omitted the
injected version property, so its passing test did not catch this build defect.

UI release versions have one source: `pom.xml`. Packaging reads that value;
Maven filters it into `build-info.properties` for About and update discovery.
Release compatibility comes from generated manifest data, not hard-coded release
cutoffs. Version numbers above record the investigated releases only; synthetic
test versions exercise the general normalization rule.

## Read-only launcher during patch preparation

Release run `39366072052` reached the compatible patch path but failed while
overwriting `previous-image/OSCAR-UI.exe` with the retained prior launcher.
[OpenJDK's Windows app-image builder](https://github.com/openjdk/jdk21u/blob/master/src/jdk.jpackage/windows/classes/jdk/jpackage/internal/WindowsAppImageBuilder.java)
marks the generated launcher read-only; Python's image copy retains that flag.
The Windows packaging wrapper now clears only that generated launcher's read-only
attribute before preparation. It does not change file bytes, fingerprint inputs,
installer authoring, or the installed baseline.

The regression starts with a read-only launcher, executes the actual PowerShell
normalization function, then prepares a compatible update and verifies the old
launcher bytes, unchanged target bytes, fingerprint and ProductCode. Native
Windows MSP generation and lifecycle validation remain required; local tests
alone do not establish update success.

The Windows build step supplies its read-only `github.token` as `GH_TOKEN`.
Previous-release and patch-chain metadata requests use it only on the fixed
repository's GitHub API endpoint. Public asset downloads do not receive the
authorization header. Local builds can supply `GH_TOKEN` or use anonymous access.
Run `39367334003` exhausted the hosted runner's anonymous API quota before
MSI preparation; authenticated metadata lookup avoids relying on that quota.

## Torch temporary-directory compatibility

Run `39367955169` built the MSI and prepared compatible inputs, then failed in
Torch's `Pdb.Load` with `TRCH0001` and a missing temporary CAB directory.
This matches [WiX issue 5778](https://github.com/wixtoolset/issues/issues/5778):
disposing its temporary-file collection removes the directory before CAB creation.
The production wrapper copies WiX into `target/windows-production/torch-tools`
and enables `Switch.System.DisableTempFileCollectionDirectoryFeature` in that
copy's `torch.exe.config`, using a .NET application runtime switch. It preserves
existing configuration and uses the copied Torch explicitly. No machine registry,
installed WiX files, application payload, or baseline identity changes.

Portable tests verify scope, preserved configuration and tool bytes.
Windows run 39368677913 (historical run; deleted during cleanup)
passed native MSP generation, patch application, repeat application, normal and
forced repair, file verification, and uninstall. This proves the installer
lifecycle, not the interactive updater flow.

## Interactive confirmation correction

The first manual Windows update test stopped before elevation because PowerShell
parsed `$Version?` in the confirmation string as a variable named `Version?`.
The prompt now uses `${Version}?`. Both local packaging tests and the Windows
PowerShell 5.1 helper test evaluate the actual prompt under strict mode without
opening a dialog. The previous MSI/MSP lifecycle tests did not exercise this UI.

Changing the installed updater helper changes the dependency fingerprint and
requires a new full-MSI baseline. Existing installations containing the broken
helper cannot repair it through this application-only MSP path. Do not edit
installed helper files or bypass baseline integrity checks. Install the corrected
full MSI, then test a subsequent compatible release through the interactive flow.

Windows run 39370659706 (historical run; deleted during cleanup)
passed the corrected helper validation and full MSI build/install/launch/uninstall.
The user confirmed installation of the v0.4.13 baseline and subsequently reported
a successful automatic update to v0.4.14 on their Windows PC. This establishes
the interactive success path for that release pair. Cancellation, failure recovery,
and reboot-required scenarios remain separate pending checks.

## Pre-release history cleanup

After the user confirmed v0.5.0 installation, releases older than v0.5.0 and
their completed workflow history were selected for deletion. v0.5.0 assets and
its workflow runs are retained; Git tags and commits remain. Historical run
identifiers above record earlier verification, but their logs are no longer
available on GitHub.

The v0.5.0 patch family originally depended on older baseline assets. Before
preparing another patch, the build now checks that the original baseline release
and its MSI still exist. A missing baseline (HTTP 404) or removed MSI starts a
new full-MSI family. Authentication, rate-limit and server failures still stop
the build. The next release after this cleanup requires full-MSI installation;
later compatible releases can patch from that new baseline.
